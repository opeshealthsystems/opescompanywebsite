# OHS Platform API — 0.115.0

Owner: OHS platform team. Support: contact@opeshealthsystems.com. Purpose: documented access to public enquiry intake, public health service offerings, partner and tester application administration, partner-institution and practitioner-programme catalogues, support service requests, published content, CRM, role-scoped operations and workforce workflows, contract and asset records, finance registers and reports, customer facility profiles, employee and HR administration, risk and performance management, validation, practitioner, recruitment, learning, surveys, account recovery, machine catalogue access, protected admin references, immutable audit-log search and detail, resource summaries, finance line items, credit notes, and user and role administration. Candidate OpenAPI `0.115.0` documents 644 registered business workflows across 462 paths (653 HTTP operations); SDK preview `0.111.0` contains the generated operation IDs and remains unpublished to a package registry. `GET /api/v1/service-offerings` publishes localized Health Data Services and Clinical Decision Support Systems (CDSS) descriptions and enquiry links; the website cards use the same application query. It describes offerings for enquiry and does not provide clinical decision functionality. The public `GET /api/v1/api-products` endpoint provides a localized, versioned catalogue of each API family, its preview status, authentication method, scope, access paths and data boundaries. Finance-scoped payroll run detail includes an allowlisted aggregate deduction total shared with the administrator view. Developer access submissions store structured application, callback, requested-scope and intended-use data; administrators review them through scoped paginated list and detail endpoints before provisioning credentials. Signed-in developers can manage their own public PKCE applications in `/en/developers/console` or `/fr/developers/console`; the site console and API use the same owner-scoped query and command workflows, and public clients receive no secret. Administrators can inspect a machine client's 30-day UTC usage under the separate read-only `api-clients:read` scope and assign or clear its daily/monthly quota under `api-clients:manage`. Client credentials remain unlimited until a limit is configured. The API also provides admin-scoped delivery metadata and confirmed-receipt reconciliation for website-form mail without exposing form content or resending mail. Partners can read approved organizations explicitly linked to their account, update limited organization profile fields, and manage linked members as an owner; membership writes require idempotency and preserve at least one owner. Administrators retain organization membership lifecycle controls. Practitioners can take published course assessments through enrollment-checked APIs, save attempt progress, receive server-scored results and review answers after submission. Partner-membership and course-assessment migrations are applied in production. Machine-client usage remains scoped to the calling integration. Delegated users can read 30 days of API usage for their own account and the current OAuth application only, with the `identity:read` scope. SDK `0.111.0` is prepared as a downloadable server-side preview and has not been published to a package registry.

The practitioner application payout command is available at `POST /api/v1/practitioners/applications/{application}/payout`. It requires an active administrator, the reviewed `practitioners:write` delegated scope, and an `Idempotency-Key`. A `202` means the request was durably accepted, not that settlement completed. Read the application resource for payout status. Provider outcomes that cannot be confirmed are held for reconciliation and are not automatically retried. Only MTN MoMo and manual settlement are available; Orange Money remains unimplemented.











Administrator-owned machine API clients can now be listed, created, rotated and revoked through `/api/v1/admin/api-clients`. These operations require an active administrator, delegated OAuth authorization and the `api-clients:manage` scope. Creation and rotation return a plaintext secret in a `Cache-Control: no-store` response. Replaying the same idempotency key and payload within its 24-hour retention window can return the same response; client lists and domain events contain no secret. Client-credentials clients remain limited to `catalogue:read` and `integration:read`.

Administrators can also register and revoke reviewed public OAuth applications through `/api/v1/admin/oauth-clients`. These authorization-code clients use exact HTTPS redirect URIs, user consent and S256 PKCE, and receive no client secret. The operations require an active administrator and delegated `oauth-clients:manage` scope.

Public product endpoints are `GET /api/v1/status` for a point-in-time application response and `GET /api/v1/changelog` for recent API release notes. Status does not probe dependencies or promise availability. Each endpoint is limited to 60 reads per minute per source IP.
